# 评测设计-复现污染与裁判偏差

## 先接受一个事实

评测结果不是只由“模型本身”决定，还会被很多看似细小的设计细节影响。

最典型的三类问题是：

- benchmark contamination
- benchmark sensitivity
- judge bias

## 1. 污染不是只看字符串重合

关于污染，至少有两个已经比较稳定的结论：

- `Investigating Data Contamination for Pre-training Language Models` 指出，当前很多报告里常见的 n-gram 式污染定义有局限，难以充分刻画真实污染。
- `Rethinking Benchmark and Contamination for Language Models with Rephrased Samples` 进一步指出，简单改写、翻译、复述就可能绕过字符串匹配式去重；也就是说，“没搜到字面重合”不等于“没有污染”。

这意味着：

- 公共 benchmark 默认应被视为存在污染风险。
- 公开声称“已去污染”时，要看去污染方法，而不是只看一句结论。

## 2. 排行榜对细节可能非常敏感

`When Benchmarks are Targets` 给了一个很直接的提醒：在 MMLU 这类多项选择 benchmark 上，改变选项顺序或答案提取方式，模型排名最多可以变化 8 位。

因此，多项选择 benchmark 至少要固定这些细节：

- 选项顺序
- 提示模板
- few-shot 样例
- 答案抽取规则
- 解码参数

如果这些信息没有写清楚，分数往往不可直接横向比较。

## 3. LLM-as-a-judge 很有用，但不是“真值机”

`Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena` 的信息非常关键：

- 强裁判模型可以和人类偏好达到较高一致性，论文报告 GPT-4 与人类偏好的一致率超过 80%。
- 但 LLM 裁判存在已知偏差，包括 position bias、verbosity bias、self-enhancement bias，以及有限的推理能力。

这说明 LLM judge 很适合做大规模自动评测，但不适合被当作无偏真值。

## 4. 长答案偏好是真实问题

`Length-Controlled AlpacaEval` 直接针对一个常见问题做了修正：自动评测器往往偏好更长的回答。

论文做的事情很直接：

- 不是直接看“谁赢了”。
- 而是估计“如果双方回答长度一样，偏好结果会怎样”。

它的意义不在于 AlpacaEval 本身，而在于提醒我们：开放式回答评测里，回答长度、话术风格、格式美观，都可能成为混杂因素。

## 5. 新鲜题和持续更新可以缓解污染，但不能解决全部问题

`LiveBench` 采用最近发布的数学竞赛、arXiv 论文、新闻和数据集来构造题目，并持续更新，目标是降低污染风险。

它提供了一个很实用的思路：

- 静态公开题库适合可复现研究。
- 动态更新题库更适合降低 benchmark 被“刷榜”和被训练集吸收的风险。

但这不意味着动态 benchmark 就自动没有偏差；它只是把主要风险从“陈旧公开题”往前推了一步。

## 最低复现清单

下面这份清单是基于上面文献归纳出的工程建议：

- benchmark 名称与版本
- prompt 模板与 system prompt
- few-shot 样例及顺序
- 选项顺序与答案提取方式
- 解码参数
- 模型版本或 API 日期
- 是否启用工具、检索、长上下文
- 裁判模型、裁判 prompt 与对比顺序

## 更稳妥的做法

- 对可验证任务，优先用客观评分。
- 对开放式任务，优先报告成对比较，而不是只报单模型绝对分。
- 使用 LLM judge 时，至少记录候选顺序、回答长度和 judge 版本。
- 如果结果差距很小，不要过度解读排行榜名次。
- 如果 benchmark 很公开、很老、很热门，就应默认检查污染风险。
