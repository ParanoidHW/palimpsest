1. 第一门槛：训推一致性

这里不是一个单一指标，而是五个层面分别闭环：模型层、采样层、输入层、Infra 层和评估层。每层都有自己的检查方法，不能用一个 cosine 相似度替代全部检查。

模型层：前向实现、权重转换、hidden state 和 logits。
采样层：采样策略、temperature、停止条件和 bonus token。
输入层：chat template、QA regen、hidden state 提取和 feature schema。
Infra 层：确定性计算、通信归约、padding、batch 和并发调度。
评估层：teacher-forcing 只作为训练期验证口径，必须并行做 sampled-prefix 或真实 rollout 实测。

每次运行都保存 target hash、producer commit、采样配置、layer schema、dtype、batch 形状和随机种子，并同时记录前向误差、模板差异、teacher-forcing 概率长度、greedy 长度、真实 rollout 接受长度和首个拒绝位置。

训练验证：用接受行为做门槛初筛

训练损失回答“模型是否拟合当前监督信号”，不能单独回答“新 checkpoint 是否更适合投机解码”。门槛初筛应逐步增加验证成本：先用 teacher-forcing 监控收敛，再用固定验证样本上的可计算接受代理量筛掉明显退化候选；入围 checkpoint 使用目标模型和 verifier 做逐轮 draft rollout；最后接入部署引擎确认系统收益。注意：draft rollout 同样需要目标模型推理，通常是训练阶段额外的 target 服务或算力预算，不能把它当作无 target 成本的离线评测。

1.1 先把接受长度拆成可观察的事件

设一次验证窗口最多提出 \(\gamma\) 个候选 token。令 \(a_j\) 表示第 \(j\) 个位置在此前候选都已接受时的条件接受概率；从窗口开头连续接受至少 \(k\) 个 token 的概率，是此前各位置接受概率的乘积。窗口期望接受长度等于这些前缀存活概率之和：

\[\mathbb{E}[L] = \sum_{k=1}^{\gamma} P(L \geq k) = \sum_{k=1}^{\gamma} \prod_{j=1}^{k} a_j\]
公式解释：\(L\) 是一轮实际接受的草稿 token 数；\(\gamma\) 是候选窗口上限；\(a_j\) 是第 \(j\) 个候选在前面均通过时的条件接受概率。该式回答“一轮平均能连续接受几个 token”，并说明为什么后段位置不能脱离前段单独计分。

因此，验证集至少同时记录平均接受长度、接受长度分布（含中位数和低分位）、各位置条件接受率，以及首个拒绝位置。只报单 token 命中率会漏掉“前面先失败、后续候选没有机会被接受”的情况。

1.2 按成本分层，而不是拿单一 loss 当晋级条件

层级怎么测资源与观察项能否单独放行
训练监控同一批 target 前缀上 teacher-forcing复用训练监督；看 loss、目标 token 概率或分布距离、按草稿位置拆开的趋势不能；用于发现发散、退化和位置性问题
廉价验证初筛在固定验证样本上计算 greedy 匹配或 sampling 分布重叠，并按窗口合成期望接受长度可复用 target logits/固定轨迹；看接受代理量、各位置衰减和任务/长度分桶可淘汰明显退化候选，不能证明真实 rollout 获益
Rollout 验证从相同 prompt 开始，每个 checkpoint 用自己的草稿 token 继续生成；目标模型对这些实际前缀执行验证，拒绝后按部署规则继续，再重复若干轮需要 target 推理。看真实接受长度分布、首拒绝位置和目标调用数；用相同 prompt、配置与配对随机种子控制比较噪声适合作为训练 checkpoint 的算法级晋级门槛
Serving 确认同一类 rollout 接入预定推理引擎、KV cache、批处理和并发调度，测端到端运行也需要 target 推理。额外看吞吐、首 token/逐 token 延迟、草稿与验证耗时、显存、排队和目标调用成本决定是否部署；接受长度提高本身不等于加速

两者的区别：Rollout 验证和 serving 确认都运行目标模型，也都可以执行投机解码。Rollout 验证的重点是用受控、可复现的评测 harness 比较 checkpoint 的算法行为；它可以复用一个 target 实例、限制 prompt 数和轮数，并把吞吐、并发、引擎优化排除在主要结论之外。Serving 确认则把候选放进预定部署栈，检查真实调度、缓存、批处理、并发和延迟成本。前者回答“这个 checkpoint 的接受行为是否更好”，后者回答“部署后是否更快、更省资源”。省掉 serving 系统因素会让 Rollout 验证更容易解释，但不会省掉目标模型前向计算。

1.3 多轨迹 regen：复用 target 计算，扩大 validation 覆盖

对每个 validation prompt 让目标模型按部署采样配置生成多条回答轨迹，再把这批固定轨迹提供给多个草稿 checkpoint 做对照。它比单一静态轨迹更能覆盖同一 prompt 下的不同续写，但仍属于 target-prefix 上的接受代理评估；草稿自己生成的新前缀仍需在 Rollout 验证阶段由 target 重新验证。

1.3.1 建议保存什么

  • prompt 的 token 序列、样本 ID、tokenizer 和聊天模板版本；prompt 本身不需要保存逐位置分布。
  • 每条回答的 token 序列、结束原因、随机种子、温度、top-k/top-p、停止规则，以及目标模型 checkpoint 和推理引擎版本。
  • 回答位置的 target 分布摘要：top-\(K\) token ID、对应概率，以及未保存尾部的剩余概率质量。只保存采样出的 token，不能计算可靠的分布重叠。

1.3.2 空间估算：4K 回答、1,000 个 prompt、每个 10 条轨迹

这对应 10,000 条轨迹、约 4,096 万个回答位置。若 token ID 使用 32 位、概率和尾部质量使用 FP16，单位置存储约为 \(6K+2\) 字节；粗略空间如下：

保存的 top-\(K\)估算空间
32约 7.4 GiB
64约 14.7 GiB
128约 29.4 GiB

回答 token 序列本身约 156 MiB，索引和元数据另加少量空间；若概率使用 FP32，top-64 约 19.6 GiB。空间按回答平均长度线性变化，4K 若只是上限而不是平均值，实际占用会更低。

1.3.3 10 条轨迹是否合适

每个 prompt 采 10 条可以作为初始配置：它能观察同一 prompt 的采样波动，同时不让少数 prompt 因轨迹更多而主导统计。汇总时应先在 prompt 内聚合，再跨 prompt 比较，并用 prompt 级 bootstrap 或重复子集估计不确定性。若任务和长度覆盖不足，优先增加 prompt 数；可在小样本上比较每个 prompt 1、2、4、10 条时 checkpoint 排名是否稳定。

推荐用法：先用固定多轨迹缓存和 top-64 做廉价初筛；对入围 checkpoint 再做 draft 自生成的 Rollout 验证；最终候选进入 serving 确认。top-\(K\) 缓存节省的是重复准备 target 轨迹的成本，不会消除 target 在新 draft 前缀上的验证计算。

1.4 训练目标可以感知接受长度，验证口径仍须独立

除交叉熵或分布匹配外，可加入直接偏向连续接受的辅助目标：greedy 场景提高草稿模型对目标模型所选 token 的概率；sampling 场景提高目标与草稿分布的重叠；再用窗口前缀乘积计算期望接受长度。也可以按真实 rollout 中各位置成为窗口起点的频率加权。它们是训练目标的候选设计，不是预先证明有效的门槛指标。比较时保持数据、验证 prompt、窗口上限和 verifier 一致，并分别报告训练目标与离线 rollout 结果，避免“优化的代理量同时充当自己的验收结论”。

1.5 让 checkpoint 对照尽量贴近部署

  • 输入分布：用代表线上任务的 prompt 和长度分桶；所有候选使用同一组 prompt、目标模型版本、tokenizer、模板和停止规则。
  • 生成路径：草稿必须在自己生成的前缀上继续提议，不能把完整真值前缀逐位置喂回后就称为 rollout。采样时匹配温度与截断策略；greedy 与 sampling 分开评估。
  • 验证规则：使用部署中的精确匹配或拒绝采样规则，并纳入额外接受 token、窗口上限和拒绝后的续写方式。
  • 配对比较：不同 checkpoint 在相同 prompt、配置和随机种子上做对照；同时报告总体值与任务、长度、温度分桶，避免均值掩盖长上下文或难例回退。
  • 系统校准：算法级 rollout 仍需要 target 前向，但可在简化 harness 中运行。它不含完整服务调度、批处理和通信成本；保留一小批固定 serving 测试，检查离线接受长度变化能否预测端到端收益。
建议晋级逻辑：先要求训推版本和协议一致；训练监控没有异常后进入 rollout 对照；接受长度及其低分位不退化、分桶无明显回退且草稿成本可接受时，再进入 serving 小测。阈值应由当前 baseline 的重复测量波动确定，不预设跨模型通用的固定差值。

更完整的指标定义、评测协议和常见误判见 接受长度与 rollout 验证 Topic；本节聚焦主页中的训练门槛思路。

2. 技术栈六层

模型/算子数据/轨迹损失/决策feature 传输验证调度框架交付

六层共同决定收益。更大草稿头可能增加草稿延迟；更高 feature 吞吐可能只是掩盖缓存问题；动态 verify 依赖 confidence 校准。

3. 三种生命周期

训练

检查 sampled-prefix、梯度和异步 feature 的可复现性。

Prefill

检查整段 prompt、模板、prefix 截断和 KV cache 建立。

Decode

检查少量 token、cache 追加、动态 batching、频繁验证和端到端时延。

资源依赖：回答生成与特征生产分开核算

目标模型服务承担两种不同工作：训练前可选的回答重生成，以及对已有完整 token 序列执行 prefill、提取隐藏状态。后者不需要逐 token decode；但在线提取会让目标服务在 drafter 训练期间持续占用加速卡。

资源紧张时的路径选择
  1. 先盘点已有回答。若其分布满足训练目标，可直接提取特征，避免全量重生成。
  2. 用 1--2 万条样本比较在线与固定特征。固定特征生产完成后关闭 producer，再训练 drafter；相同特征可跨 epoch 复用。
  3. 同步比较回答生成、特征生产、drafter 训练的 GPU-hours，峰值并发卡数、特征存储和读写吞吐、总 wall-clock 与接受指标。固定特征会把目标卡占用前移，但增加存储和数据搬运，不能只凭是否常驻服务判断成本。
  4. 全量缓存过大时，再测试按数据分片生产和训练，并验证 target checkpoint、层定义与样本 token 序列一致。

prompt-only 的一遍式回答生成并捕获每个 decode step 的隐藏状态，需要新增跨 worker 的 token 对齐、传输、重试和反压机制；现有 SpecForge Online capture 对完整序列做 prefill，不等于已经实现该能力。详见 训练数据生命周期中的资源分析。

6. 尚未闭合的论证链

这些问题应保留为讨论入口，而不是写成确定结论：

  • 余弦相似度 >0.999 是否足以预测接受长度？还需结合 logits、相对误差和首个拒绝位置。
  • 多个采样场景能否由一个条件化草稿模型覆盖？需要比较校准成本与专用模型维护成本。
  • regen 的收益来自目标分布、温度还是长度覆盖？必须固定另外两项做因子实验。
  • feature 新鲜度、传输和训练随机性如何共同影响收敛？应记录 feature age 与 step-level host wait。
  • 接受长度在什么 draft/verify 成本比下才转成端到端收益？用 Pareto 曲线，而不是单一 accepted length 决策。
