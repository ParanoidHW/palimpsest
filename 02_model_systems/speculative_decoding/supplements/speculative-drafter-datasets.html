Agent 评测		AgentX 页面Methodologyv1.0 全量数据v1.0 256K 数据AgentX harness
  • v1.0：393 个 session，135,282 个 request；2026-06-21 构建。

GPQA-Diamond
专家推理		Hugging Face 数据集页（访问受限）官方代码论文
  • 规模：GPQA 全集 448 道选择题；Diamond 是其中经过更严格筛选的 198 题子集。HF 仓库标记为 gated/auto，API 不公开样本级 split 统计，故 Diamond 数量依据原论文及官方资料，而非 HF API 的计数。
  • 领域：生物学、物理学和化学等研究生阶段科学问题；问题由领域专家编写。
  • 难点：原论文以非专家检索作答的低成功率说明题目难度；Diamond 子集进一步筛选专家间一致性较高、题目质量较好的样本。
  • 题型：四选一，包含题干、选项及标准答案；输入 token 长度会随选项打乱、提示模板和解析格式变化，应在实际 harness 中统计。
  • 适用：检验投机解码下高难科学知识题的最终回答是否保持正确；它不直接测加速。
  • 专家编写并经过专家作答/验证，不是模型生成的推理轨迹。
  • HF 仓库受访问门控保护，本次只能核验仓库存在及修订标识，不能直接读取其 gated 文件或确认其中子集映射；不要把全量 GPQA 与 Diamond 混称。
  • 题库没有统一生成模型；被测模型由论文实验指定。
  • 多选项随机打乱或选项标签变换可能改变结果，必须报告具体评测协议。
  • 使用四选一准确率；固定 GPQA 子集、仓库授权版本、选项顺序/打乱种子、提示模板、答案抽取和外部工具使用情况。
  • 若论文只写 GPQA 而未写 Diamond，不应自动把其结果映射到 GPQA-Diamond。
  • 投机解码评估还应并报答案准确率、接受长度和端到端时延。
HumanEval
代码生成		OpenAI 官方代码Hugging Face 数据集页论文
  • 规模与 split：HF 仓库只有 test split，共 164 道 Python 函数补全题。
  • 字段：task_id、prompt、canonical_solution、test 和 entry_point。评测输入主要是函数说明、签名和代码前缀；测试程序与参考实现用于判分，不应作为模型提示泄漏。
  • 任务：补全符合题意且能通过隐藏单元测试的 Python 函数。
  • 指标：pass@1、pass@k；统计值受温度、每题采样数与 pass@k 估计方法影响。
  • 安全边界：必须在隔离环境执行模型代码；字符串相似度不能替代运行测试。
  • OpenAI 研究人员编写函数说明和参考实现，并配套单元测试。
  • 这是程序合成评测题，不是对话训练轨迹；HF 当前只发布评测 test split。
  • 数据集没有统一的生成模型；被测模型由实验配置指定。
  • Python 运行时和依赖版本会影响测试结果，需固定并记录。
  • 按每题生成一个或多个候选程序，在沙箱中运行隐藏测试，再计算 pass@k。
  • 固定 HF 修订、prompt 后缀处理、Python 版本、超时、内存限制、随机种子、temperature、top-p 和采样数 n。
  • 报告投机解码结果时同时给代码通过率、生成 token 数、接受长度和端到端时延。
HumanEval+
代码生成		EvalPlus 官方代码Hugging Face 数据集页论文
  • 规模与 split：HF test split 共 164 题，与原 HumanEval 的题目一一对应；该仓库当前数据文件约 10.96 MB，下载文件约 2.90 MB。
  • 字段：task_id、prompt、canonical_solution、entry_point 和 test。每题仍需生成 Python 函数，但判分采用扩展后的测试集。
  • 增强测试：EvalPlus 通过测试生成与变异扩展每题测试用例，以增加边界输入覆盖，发现仅通过原始少量测试的错误实现；不得将 HumanEval 原版通过率与 HumanEval+ 分数混作同一设置。
  • 指标：pass@1/pass@k；严格度提高可能降低分数，但不能据此认为模型生成能力变差。
  • 复用 HumanEval 的 164 道题和参考程序，并为测试用例做自动扩展与检查。
  • 不是新增一套独立题目，也不是训练数据集。
  • 题目没有新的统一生成模型。
  • 测试扩展来自 EvalPlus 测试生成流程；复现时锁定 EvalPlus 代码、数据仓库修订和测试集合。
  • 使用 EvalPlus harness 在沙箱中执行生成代码，并运行增强测试。
  • 固定 HumanEval+ 仓库修订、Python 与依赖、资源限制、temperature、top-p、采样数 n 和 pass@k 算法。
  • 与 HumanEval 并列报告时明确标注原始测试与增强测试，避免把测例数量差异当作投机解码效应。
LiveCodeBench
代码生成		项目主页官方代码Hugging Face 代码生成数据集论文
  • 范围：LiveCodeBench 是持续更新的基准，不能把一个固定总量当成永久规模。HF 代码生成数据卡在当前修订说明收录 400 道题；此数字只代表该发布快照，不等于整个项目的所有任务或最新题量。
  • 来源：编程竞赛网站的公开题目，HF 数据卡当前快照列出 LeetCode、AtCoder 和 Codeforces；每题包含题面、输入输出样例和隐藏测试，平均隐藏测试超过 59 个。
  • 防污染设计：题目标注发布日期和难度，可以按时间窗口筛选较新的题目，降低训练语料污染风险；复现必须锁定截止日期或题目范围。
  • 评测范围：LiveCodeBench 项目涵盖代码生成、自我修复、测试输出预测和代码执行等能力；这里链接的是代码生成场景，不能把单一 HF 子集代表整个基准。
  • 指标：按官方 harness 执行候选代码并计算通过率/pass@k，具体汇总随任务类别与版本而异。
  • 来源为公开竞赛编程题及其测试用例；题目由竞赛平台或命题者提供，不是统一模型生成的对话轨迹。
  • HF 数据卡的 400 题属于其当前代码生成快照；官方仓库会持续更新，应注明题目时间范围和数据修订。
  • 题目数据没有统一生成模型；生成答案的是被测模型。
  • 测试程序、运行环境和时间限制会直接影响代码是否判为通过，需随模型结果一起锁定。
  • 用官方评测代码装载指定日期窗口的题目，在受限环境运行生成程序并核对隐藏测试。
  • 固定 HF/API 或官方仓库修订、任务类别、发布日期范围、编程语言、依赖、超时、温度、每题采样数与答案提取规则。
  • 投机解码对比应在相同题目快照、target、采样协议和执行器下进行，并同时记录代码通过率、接受长度与端到端时延。
LongBench v2
长上下文		Hugging Face 数据集页（当前维护仓库）原发布仓库LongBench 官方代码论文
  • 规模与题型：503 道四选一问题，HF 数据卡将输入统一为题目、A–D 选项、标准答案和长上下文。
  • 长度口径：HF 数据卡报告上下文约 8K 至 2M 词，多数低于 128K 词；这不是 token 数，不能直接写成模型 token 长度。实际 token 数随 tokenizer、上下文文本和包装提示而变，应对使用版本重新统计。
  • 六类任务：单文档问答、多文档问答、长上下文学习、长对话历史理解、代码仓库理解、长结构化数据理解。
  • 难度与覆盖：约 100 位不同专业背景的高学历参与者协助构建，并经自动和人工复核；数据卡报告人在 15 分钟限制下的准确率为 53.7%。这说明题目难，但不能替代目标模型的实际质量评测。
  • 适用：检查投机解码面对长上下文 prefill、长 KV cache 和长距离信息整合时的质量与速度；不能把它当作专门的解码吞吐基准。
  • 题目与上下文来自真实长文档、多文档材料、对话记录、代码仓库及结构化数据，由近百位参与者构造并经过自动与人工检查。
  • HF 当前维护页面为 zai-org/LongBench-v2，旧地址 THUDM/LongBench-v2 会重定向/迁移；对照论文时需要核验具体版本和字段，不应只依旧路径推定当前仓库 owner。
  • 数据集不是统一模型生成的回答轨迹；评测模型由实验配置指定。
  • 题目有固定 A–D 选项与答案。若提示中重排选项，需同步重映射标准答案并记录随机种子。
  • 按选择题答案计算准确率；仓库提供数据下载，完整自动评测需使用 LongBench 官方代码。
  • 固定仓库修订、上下文裁剪/拼接方式、tokenizer、模型上下文窗口、选项排列、提示模板和答案抽取规则。
  • 长上下文比较应报告实际 prompt token 数分布、prefill 与 decode 时延、KV cache 占用、接受长度及答案准确率。

SPEED-Bench 的数量和任务结构来自其 Hugging Face 数据卡（通过 hf-mirror.com 读取）；“当前公开配置合计”按 HF API 中六个配置相加，不能替代对具体实验 split 的记录。AgentX 的规模、轨迹字段、重放图构造和 warmup 规则来自其 Methodology 页面；原始 provider 模型未公开，且 AgentX 不评价合成 token 的答案质量。

采用关系以已核实的论文分析为准；“未确认直接采用”表示当前分析未提供证据，不代表原论文没有使用。相关技术解释见投机草稿模型技术栈与思考。
