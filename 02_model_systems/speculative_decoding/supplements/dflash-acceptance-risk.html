核心判断

目标“草稿 8 个 token，平均接受 6-7 个”是一个很高的目标，需要先统一指标口径。DFlash 论文中的 acceptance length tau 有时按 speculative decoding cycle 统计，可能包含 target model 额外产出的 bonus token；如果你们说的是“8 个 draft token 里接受 6-7 个”，那对应到含 bonus token 的口径可能是 tau=7-8，比表面看起来更激进。

如果把每个位置的命中率粗略视为相同且独立，8 个 draft token 的期望接受数为 sum_{k=1}^{8} p^k。达到平均接受 6 个需要单位置条件命中率大约 93%-94%；达到 7 个需要接近 97%。真实场景里越靠后的 token 更难，所以应重点看 position-wise accuracy 和 fail-position 分布，而不是只看均值。

公开 DFlash 结果说明这个目标在部分短输出、greedy、数学/代码任务上有机会接近，但在 chat、temperature sampling、长输出、生产并发场景下风险明显更高。DFlash 在 Qwen3-8B、block size 16、temperature=0 的平均 tau 约 6.49，数学任务可到 6.54-7.87，代码任务约 5.95-7.27，MT-Bench 约 4.24。若换到 block size 8 的 ablation，公开结果反而多在 3-5 左右。因此“8 draft token 接受 6-7”不能直接从 DFlash 主表外推，必须按你们自己的目标模型、数据域、解码参数和口径验证。

需要考虑的维度

1. 指标口径

明确 block size 是否包含 anchor token、是否包含 target bonus token、接受长度是 greedy exact match 还是 speculative sampling 接受概率。建议同时记录 accepted_draft_tokens、accepted_with_bonus、full_block_accept_rate、P(accept>=k)、position-wise top-1 match、首错位置分布。

2. 目标业务分布

接受率首先是 workload 指标，不是模型通用指标。数学、代码、结构化输出通常高于开放聊天；短输出高于长输出；greedy 高于 sampling；低熵上下文高于高熵上下文。评估集必须按线上流量拆分，而不是只报一个总均值。

3. 数据构造与目标对齐

DFlash 的经验是使用 target model 生成的 responses 来构造训练集，而不是直接使用原始数据答案，这能减少 draft-target 分布偏移。训练数据需要覆盖 prompt 类型、输出长度、推理痕迹、代码格式、工具调用或 JSON 约束等线上模式。

4. masked block 构造

DFlash 不采用普通 block diffusion 的固定分块随机 mask，而是随机采样 response 中的 anchor token，把 anchor 作为 block 首位置，mask 后续位置，训练 draft 并行预测后续 token。这更贴近推理时“上一轮 target 验证后的 clean token 作为起点”的模式，也是提升接受率的关键设计。

5. target feature 注入方式

公开经验显示，只让小 diffusion drafter 从 token 上下文“凭空猜未来”接受长度有限。DFlash 的关键是抽取 target model 多层 hidden states，融合后作为 KV 注入到 draft model 每一层。DFlash ablation 里，无 target feature 的 5 层 diffusion draft 只能达到约 3-4 的接受长度；KV injection 明显优于只在输入层 fusion。

6. target hidden layers 数量与选择

DFlash 默认从 target model 的浅层到深层均匀抽取 5 层 hidden states，通常比 3 层更好。DF LARE 的进一步经验是，让每个 draft layer 学习不同的 target-layer 融合权重，可以继续提高 draft 深度可扩展性，避免所有 draft 层共享同一个 fused context 导致收益饱和。

7. draft 模型容量

draft 层数越多，接受长度通常越高，但端到端速度不一定更高。DFlash ablation 中 8 层 draft 的接受长度高于 5 层，但 5 层在整体 speedup 上更优。若你们的第一目标是接受率，可以试 5/7/8 层；若目标是 serving 成本，需要用 acceptance-latency Pareto 选型。

8. block size 训练与推理匹配

DFlash 经验是，用更大的 block size 训练可以较好泛化到较小推理 block size，反过来不成立。即使线上只 draft 8 token，也值得比较 train block 8 -> infer 8 与 train block 16 -> infer 8。公开 ablation 还显示 block-8 模型在 Math500 上经常整块全接受，可能存在容量或训练信号未充分利用的问题。

9. loss weighting

因为早期 token 一旦错，后续 token 都无法被接受，训练 loss 应更重视 block 前部位置。DFlash 使用指数衰减位置权重，block size 8 的 decay gamma 公开配置为 4；DF LARE 进一步使用 progressive position weighting，先重视前部收敛，再逐步覆盖后部 token。

10. 上下文长度与生成长度

长输出是接受率最大风险之一。Test-Time Speculation 的公开观察是，DFlash、EAGLE-3、PARD 等 speculator 在长响应中 acceptance length 会随生成位置下降，几千到数万 token 后可能接近 1。DFlash 也显示 4K 训练的 base drafter 在 8K/16K/32K context 会退化，而少量 long-context fine-tune 可显著恢复。

11. 解码参数

temperature、top-p/top-k、重复惩罚、logit bias、grammar/JSON constraint、stop sequence 都会改变 target 分布。如果训练按 greedy top-1 对齐，线上却大量 sampling，接受长度会下降。需要分别评估 temperature=0、线上默认 sampling、极端高熵请求。

12. serving 实现

平均接受数高不等于 speedup 高。速度取决于 draft latency + verification latency + scheduler overlap + batch/concurrency + KV/cache overhead。DFlash 在 SGLang/FA4/Spec-v2 overlap 下效果强，但高并发时 speedup 会下降。上线决策必须看 tok/s、p50/p95 latency、GPU utilization，而不是只看接受长度。

13. 模型与 tokenizer 绑定

draft 必须和 target tokenizer、embedding/LM head、特殊 token、chat template、RoPE/context 设置、logit processors 对齐。target 模型版本变更、SFT/RLHF 更新、template 更新都可能让接受率掉，需要纳入回归测试。

14. 数据规模与质量

DFlash 主结果约用 800K target-generated samples；DF LARE 把训练集扩到 2.4M，并报告 acceptance length 与 speedup 随数据继续提升。经验上，数据规模、目标域覆盖、target-generated response 质量，可能比盲目加 draft 层数更稳。

业界/论文经验可参考

1. DFlash 的关键经验

使用 block diffusion 一次并行 draft 多个 token，避免 autoregressive drafter 的逐 token 延迟；用 target hidden states 做 KV injection；随机 anchor masked blocks 对齐推理行为；共享 target embedding 和 LM head；早期位置加权训练。主结果在 Qwen3-4B/8B 上显著高于 EAGLE-3，但 chat 和 sampling 场景接受长度明显低于数学/代码 greedy 场景。

2. DF LARE 的扩展经验

DFlash 的一个瓶颈是所有 draft 层共享同一个 fused target context，draft 深度增加后收益会饱和。DF LARE 使用 layer-wise adaptive fusion 和更深 draft layers，让每个 draft layer 接收不同的 target-layer 组合；同时扩大训练数据到 2.4M，报告 Qwen3-4B/8B/GPT-OSS-20B 上平均 wall-clock speedup 进一步提升。对你们的启发是：如果 5 层 DFlash 卡在 5.x 接受长度，下一步优先检查 per-layer conditioning，而不是只粗暴加层。

3. EAGLE 系列经验

自回归/树状 draft 可以提升接受长度，但 draft cost 和 verification cost 会随 draft steps/tree size 增长。DFlash 论文中 EAGLE-3 tree size 60 的接受长度仍低于 DFlash block diffusion，且验证开销更高。对你们的启发是：不要单纯追“候选更多”，要追单位 draft/verify 成本下的有效接受 token。

4. 长输出经验

Test-Time Speculation 指出，offline-trained speculator 在长输出时容易因为训练上下文短、推理轨迹长而逐步偏离 target 分布。它用验证阶段已有的 target distribution 做 test-time distillation 来恢复接受长度，但会引入 backward/optimizer step 开销。对你们的启发是：即便第一版不做 TTS，也要按 generated-token bucket 监控接受长度，例如 0-1K、1-4K、4-8K、8K+。

5. serving 经验

speculative decoding 是系统工程问题。公开结果通常会区分 Transformers、SGLang、vLLM、FlashAttention backend、concurrency、是否有 scheduling overlap。上线判断要以生产框架复现实测为准，paper 上的 acceptance length 只能作为方向参考。

建议的验证路径

1. 先做离线 metric harness

固定 target model 和线上 chat template，复现 vanilla target 输出；实现 draft/verify 日志，逐请求记录 acceptance histogram、position-wise match、首错位置、上下文长度、生成位置、任务类型、temperature、latency。

2. 做小规模 100K ablation

建议至少比较：

  • target feature: none vs input fusion vs KV injection
  • hidden layers: 3 vs 5 vs 9
  • draft layers: 3 vs 5 vs 7/8
  • train/infer block: 8->8, 16->8, 16->16
  • loss: uniform vs exponential decay vs progressive weighting

3. 用目标口径设 gate

如果目标是“8 个 draft token 平均接受 6-7 个”，建议 gate 不只看 mean：

  • overall mean accepted draft tokens >= 6.0
  • core workload mean >= 6.5
  • weakest important domain >= 5.0
  • P(accept>=6) 达到线上收益要求
  • 生成位置 4K+ 后不明显塌陷
  • 端到端 tok/s 和 p95 latency 确实优于 baseline

4. 再扩大数据和长上下文

如果小规模 ablation 证明 KV injection + block 16 train -> block 8 infer 最优，再扩到 800K 以上 target-generated samples；如果线上有长 reasoning/code 输出，应加入 long-context fine-tune 或至少做长输出分桶评估。

5. 上线前做 drift 回归

target model、tokenizer、chat template、logit processor、serving backend 任一变化，都跑 acceptance regression。草稿模型本质上绑定 target 分布，不能当成独立可迁移组件。

对当前目标的风险评估

“8 draft token 接受 6-7”可以作为核心业务域、greedy 或低温、短到中等输出的 stretch goal；如果希望在所有线上请求平均达到这个水平，风险较高。公开 DFlash 的主表高接受长度多来自 block size 16 和特定 benchmark；block size 8、chat、高温、长输出场景都可能显著低于 6。

更稳妥的第一阶段目标是：先在核心高价值域达到平均 6+，同时保证端到端 speedup；然后通过数据扩容、layer-wise fusion、长上下文适配，把弱域和长输出拉上来。

下一步需要确认的问题

1. 你们的 target model 是哪个系列和大小，是否已经固定 tokenizer/chat template？

2. “草稿 8 个 token”里的 8 是否包含 anchor/bonus token，还是纯 candidate draft tokens？

3. 线上主要是 greedy、低温 sampling，还是高温开放聊天？

4. 目标业务分布里数学、代码、普通 chat、长 reasoning 各占多少？

5. 你们更在意平均接受长度、吞吐 tok/s、首 token 后延迟，还是 GPU 成本？

answer metric-definition

bonus token 指的是：在一次 draft-verify 循环里，除了被接受的草稿 token 之外，target model 还能顺手产出的那个额外 token。

典型流程是：

1. draft model 先猜 8 个 token: d1 ... d8
2. target model 一次 forward 验证这 8 个 token
3. 假设前 6 个 draft token 被接受，第 7 个不匹配
4. target model 会在第 7 个位置给出自己的正确 token

这个 target 产出的额外 token，不是 draft 猜出来的，但可以作为本轮输出推进的一部分，所以常被叫做 bonus token。如果 8 个 draft token 全部被接受，target 通常也可以基于最后一个 draft token 的 hidden state 再产出下一个 token，也算一个额外 token。

因此统计口径需要拆开：

accepted_draft_tokens = 6
accepted_with_bonus = 7

如果目标是“8 个 draft token 里真的接受 6-7 个”，这是口径 A；如果目标是“本轮总推进 6-7 个 token，其中包含 target bonus token”，这是口径 B。口径 A 更难，因为它要求 draft 自己命中 6-7 个；口径 B 可能实际只要求 draft 命中 5-6 个。

answer block-size anchor-token

在 DFlash 语境里，anchor token 是每个 draft block 的起点 token：它已经由 target model 真实生成并验证过，不是草稿模型要猜的 token。

推理时可以这样理解：

已确认上下文: ... x_t        <- anchor token / clean token
draft 要猜:   x_{t+1} ... x_{t+8}

如果目标是“口径 A：8 个 draft token 里接受 6-7 个”，工程上建议把 block size 明确定义为 8 个 candidate draft tokens，不包含 anchor token。

但 DFlash 论文和部分实现里的写法可能是：

[anchor, mask, mask, mask, ...]

也就是 block 的第一个位置是 clean anchor，后面 block_size - 1 个位置才是模型并行预测的 draft tokens。因此如果论文或代码里 block_size=8，它可能实际只预测 7 个 candidate token：

paper-style block_size = 8
= 1 anchor + 7 draft candidates

而当前目标是：

candidate_draft_tokens = 8
average accepted_draft_tokens = 6-7

那在这种实现口径下，可能需要配置：

internal block_size = 9
= 1 anchor + 8 draft candidates

关键是不要只看变量名 block_size，要看代码里 mask 的位置数量。建议在日志和评估结果里直接记录：

anchor_tokens = 1
candidate_draft_tokens = 8
accepted_draft_tokens = 6
bonus_token_excluded = true

这样不会和论文里的 tau、block size 口径混淆。

更新后的目标口径

当前 target model 先按 DSV4 规划，Flash/Pro 暂未最终确定。由于 draft model 强绑定 target 分布，Flash 和 Pro 如果 logits、tokenizer、chat template、reasoning mode 或服务端 logit processor 有任何差异，都应视为两个 target，各自训练或至少各自评估。

用户确认“8 个可以包括 anchor/bonus”。因此第一阶段可以把工程目标定义为：

accepted_with_bonus around 6-7 per cycle
candidate_draft_tokens <= 8

但为了避免指标误判，评估里仍需同时记录：

candidate_draft_tokens
accepted_draft_tokens
bonus_token_count
accepted_with_bonus
full_candidate_accept_rate
first_reject_position

做低时延 infra 验证时，可以用包含 bonus 的 tokens advanced per verify 作为主指标，但训练诊断仍看不含 bonus 的 accepted_draft_tokens。

Chat Template 建议

chat template 必须在训练数据生成、draft 训练、离线评估、线上 serving 四个环节完全一致。它不是外围格式问题，而是 draft-target 对齐的一部分。建议先做一个 frozen template contract，再开始大规模生成 target responses。

建议 contract 至少包括：

model_id / checkpoint_id
tokenizer revision
chat template revision
system prompt policy
role tokens and separators
assistant prefill format
reasoning / non-reasoning mode
tool-call / JSON mode policy
EOS / stop token policy
logit processors
sampling parameters
max context / RoPE setting

如果 DSV4 Flash/Pro 的官方 template 尚未明确，第一版 infra 验证不要自行发明复杂 template。可以选一个最小、稳定、可复现的 template：

<system> optional fixed system prompt
<user> user content
<assistant>

同时保留 template revision 字段。后续一旦切换到官方 template，需要重新跑 acceptance regression；如果差异大，draft 需要重训或微调。

对于 reasoning 模式，如果 DSV4 有 thinking/non-thinking 或类似开关，第一阶段只选一种。低时延验证优先从 non-reasoning / normal chat 模式开始，因为输出更短、路径更稳定、验证周期更快。若 infra 目标最终覆盖长 reasoning，再单独建 reasoning 数据集和长输出评估，不要混在第一阶段里。

解码策略建议

第一阶段建议按 greedy 做。原因是 speculative acceptance 的上限由 draft 和 target 的分布一致性决定，greedy exact-match 最容易诊断，也最接近 DFlash 主结果的高接受率场景。

推荐阶段：

1. Greedy-only proof of capability：固定 temperature=0，禁用会引入额外随机性的 logit processor，目标是证明 DSV4 + DFlash 路线能在可控场景达到高 accepted_with_bonus 和低延迟。

2. Low-temperature compatibility：第一阶段通过后，再测线上可能需要的低温 sampling，例如 temperature=0.2-0.6，主要观察 acceptance 会掉多少。

3. Production policy regression：最后用真实 serving policy 回归，包括 stop sequence、JSON/tool constraints、重复惩罚等。任何 processor 不一致都会导致 draft-target mismatch。

通用场景 vs 特定场景

“通用场景”不建议作为第一阶段验收目标，因为 acceptance rate 对 workload 太敏感。infra 验证可以分成两层：

Layer 1: controlled high-acceptance benchmark
Layer 2: broad generality stress test

Layer 1 用来证明低时延能力上限，可以优先选择接受率更容易高的场景：

  • deterministic QA / short instruction
  • code completion 或代码补全式任务
  • math short/medium reasoning，但先不要上超长 CoT
  • structured generation with stable format

Layer 2 再覆盖通用 chat、开放创作、多轮对话、长 reasoning、代码生成长输出。这里的目标不是一开始都达到 6-7，而是看 acceptance 分布、退化位置和系统是否仍有收益。

建议验收口径：

primary demo slice: accepted_with_bonus >= 6.5 / 8
general mixed set: report by domain, no single average hiding weak domains
long output buckets: 0-1K, 1-4K, 4K+
latency: p50/p95 inter-token latency and end-to-end tok/s

低时延 Infra 验证下的优先级

既然更在意低时延能力验证，优先级应是：

1. 接受率上限优先于通用性

2. greedy 优先于 sampling

3. 单/低并发 latency 优先于高并发吞吐

4. 先证明 DSV4 某个固定版本可加速，再扩到 Flash/Pro 双版本

5. 训练配置先选高接受率方案，再做 speed Pareto

推荐第一版配置假设：

target: DSV4 fixed checkpoint, Flash or Pro 二选一先 pin 住
mode: non-reasoning / normal chat
decode: greedy
candidate draft tokens: 7 or 8
metric: accepted_with_bonus target 6-7
training block: compare internal block 8/9/16 depending on anchor definition
target features: KV injection required
target hidden layers: start with 5, ablate 3/9
draft layers: start with 5, ablate 7/8 if acceptance不足
loss: exponential position decay, then test progressive weighting
data: target-generated responses, first 100K ablation, then 800K+

1. SpecForge vs vLLM speculators

公开资料显示，两者都已经把 DFlash/block diffusion speculative decoding 放进支持范围，但定位不同。

SpecForge 更像 SGLang 生态里的 speculator 训练与集成框架。它的优势是和 SGLang serving、Spec-v2 scheduling overlap、EAGLE/DFlash 等推理路径更贴近；如果最终 serving 也走 SGLang，训练产物到推理验证的摩擦会小。劣势是生态相对更偏 SGLang，训练代码和高性能路径很可能默认 CUDA/GPU，迁移到昇腾 NPU 时要重点查自定义 attention、Flex Attention、FlashAttention、CUDA graph、kernel 依赖。

training framework: 需要能在 torch_npu / Ascend 上跑 DFlash 训练

2. 模型结构上如何提高接受率

DFlash 接受率的核心不是“draft 层长得像谁”，而是 draft 能否稳定消费 target hidden features，并把这些 features 转成未来 token 的高置信预测。因此结构建议按优先级看：

1. 必须做 target feature KV injection

无 target feature 的 diffusion drafter 接受长度明显受限。对 DSV4 来说，draft 结构是否复用 DSV4 layer，优先级低于“能否正确、稳定、高带宽地注入 DSV4 多层 hidden states”。

2. draft hidden size / attention head / norm 尽量贴近 target feature 空间

如果 DSV4 hidden size 很大，而 draft hidden size 过小，projection 会成为语义瓶颈。可以从较小 draft 起步，但建议 ablate draft width，而不只 ablate depth。低时延目标下，width 增大会提高 draft latency，需要和 acceptance 一起看 Pareto。

3. 是否采用 DSV4 结构

如果 DSV4 是 MoE 或有特殊 attention/norm/MLA/GQA/SWA 设计，直接照搬完整结构未必划算。draft model 的目标不是复现 target，而是在很低成本下利用 target features。建议采用“兼容 target 表征的轻量层”，而不是一开始完整复刻 DSV4。

4. 是否使用 DSV4 部分权重初始化

有潜力，但要谨慎。可能有帮助的部分：

   token embedding / LM head: 尽量共享或初始化自 target
   RMSNorm / input-output projection: 可从 target 风格初始化
   attention/MLP weights: 只有当 draft layer 结构、hidden size、head layout 对齐时才考虑

风险是 DSV4 的层权重是在 autoregressive full model 中工作的，直接移植到 block diffusion masked positions + KV injected target context 下，未必比专门训练的轻量 draft 更好。尤其如果 target 是 MoE，复制 expert/route 结构会显著增加 draft cost，低时延目标可能不划算。

5. SWA / sliding window attention

draft block 本身很短，核心上下文来自 target hidden KV injection。SWA 对 draft 自身 block 内 attention 的收益可能有限，但对长上下文 draft self-attention 成本有帮助。第一阶段不要把 SWA 当成接受率关键项；可以先用最简单稳定的 causal/block attention，确认 acceptance，再引入 SWA 优化延迟。

6. layer-wise target feature fusion

这是比“照搬 DSV4 layer”更值得优先尝试的结构改动。DFlash 是多层 target hidden states 融合成一个 shared context，再注入所有 draft layers；DF LARE 的经验是让每个 draft layer 学不同的 target-layer 融合，可以突破深度扩展收益饱和。对 DSV4 这种大模型，建议把 layer-wise fusion 作为第二阶段结构优化。

建议结构路线：

Stage A: Qwen3-DFlash-like lightweight draft + DSV4 embedding/LM head + DSV4 hidden KV injection
Stage B: ablate draft depth/width + hidden layer count
Stage C: add layer-wise adaptive fusion
Stage D: test DSV4-style layer components or partial initialization

不建议第一步就完整采用 DSV4 结构，因为会把训练风险、NPU kernel 风险、低时延风险同时放大。

3. 自蒸馏是否能提高接受率

可以，而且应该把它视为提高接受率的主线之一，但要区分三种蒸馏。

第一种是 offline target distillation，也是 DFlash 的基本做法：训练数据使用 target model 生成的 responses，并用 target hidden states / logits 监督 draft。这不是简单 next-token CE，而是让 draft 对齐固定 target 的行为分布。建议必做。

第二种是 logits distillation。除了对 target token 做 CE，还可以对 masked positions 蒸馏 target logits 分布，例如 KL(target logits || draft logits)。这对 sampling 或高熵位置更有帮助；对 greedy exact match，也能改善 top-2/top-3 排序，减少边界错。成本是需要保存或在线计算 target logits，存储和训练开销更大。可以只对前 K 个 draft positions、top-k logits 做蒸馏，避免全 vocab KL 太重。

第三种是 online/test-time distillation。Test-Time Speculation 的思路是利用 verify 阶段 target 已经算出的分布，边生成边更新 draft。它能缓解长输出接受率下降，但会引入 backward/optimizer 开销。对于你们低时延 infra 验证，第一版不建议把 online update 放进主路径；但可以作为长输出场景的增强实验。

更实用的自蒸馏方案：

1. 用 DSV4 greedy 生成训练 responses
2. 对 anchor 后 7/8 个位置提取 target hidden states
3. 训练 draft 做 weighted CE
4. 追加 top-k logits KL，只蒸馏前几个关键位置
5. 用当前 draft 跑验证，收集 rejected cases
6. 对 rejected-heavy contexts 做 hard example replay / second-stage fine-tune

这里的“自蒸馏”本质上是 target-to-draft distillation，不是 draft 自己教自己。真正的 draft self-training 风险较大，因为 draft 错误会强化自身偏差；如果做，也应始终用 target verify/logits 过滤。

4. 选择哪些 target 特征层

DFlash 公开经验是从 target model 的浅层到深层均匀选择 5 层，范围大致避开最早和最后的极端层，例如从第 2 层到倒数第 3 层之间均匀采样。直觉是：

浅层: lexical / local syntax
中层: semantic / task state
深层: next-token decision features
最后几层: 过度贴近 logits head，可能更尖锐但泛化未必最好

业界没有一个对所有模型固定最优的层号。对 DSV4 应该做小 ablation，而不是直接相信 Qwen3 的层号。建议按 normalized depth 选层，而不是绝对层号：

3-H: 25%, 50%, 75%
5-H: 10%, 30%, 50%, 70%, 90%
7-H: 10%, 25%, 40%, 55%, 70%, 85%, 95%

同时建议额外测试“偏深层”组合：

deep-5: 50%, 62.5%, 75%, 87.5%, 95%
mid-5: 25%, 37.5%, 50%, 62.5%, 75%
wide-5: 10%, 30%, 50%, 70%, 90%

如果 DSV4 是 MoE，层选择还要看 router/expert 行为是否稳定。可以记录每层 hidden state 对 target next-token logits 的线性 probe 准确率，或训练很小的 probe 预测后续 token，用它来筛层。更工程化的办法是：

1. 冻结 target，采样一批线上/benchmark prefixes
2. 对每个候选层 hidden state 训练轻量 probe 预测 next token / next 4 tokens
3. 选 probe 表现高且层间互补的 5 层
4. 再进入完整 DFlash draft 训练

对接受率而言，层的互补性比单层最强更重要。只选最后几层可能冗余高；均匀跨层通常是强 baseline；layer-wise adaptive fusion 可以减少人工选层压力。

EAGLE-3 和 DFlash 训练本身的差异

两者差异很大，不能把 EAGLE-3 training pipeline 简单换个模型名当 DFlash 用。

EAGLE-3 的核心是 autoregressive/tree-style draft。训练通常学习从 target hidden states 和 token embeddings 预测下一步/多步 token，draft 过程仍带有逐步生成或 tree expansion 的味道。训练样本的关键是 target hidden states 与下一个 token 的对齐；模型常常是一层或少量 transformer layer，训练目标更接近 next-token CE / tree draft policy。

DFlash 的核心是 anchored block diffusion draft。训练时随机采样 anchor token，把 anchor 后面的 block positions mask 掉，让 draft 在一个 forward 里并行预测多个 future tokens。它需要：

random anchor sampling
masked block construction
block attention / sparse attention mask
target multi-layer hidden states as context
KV injection or equivalent conditioning
position-weighted loss
block size / max anchors
full-block and first-reject metrics

因此 DFlash 比 EAGLE-3 多了几个训练专属问题：

1. block size 是否含 anchor，训练/推理必须一致。

2. anchor sampling 分布直接影响接受率。

3. 早期位置错误会截断整个 block，所以 loss weighting 更关键。

4. target hidden states 不只是辅助输入，而是每层 draft 的主要条件信息。

5. 验证时是 chain/block verify，不是 EAGLE tree verify。

6. draft latency 对 block size 不线性增长，但 verify cost 会增长。

EAGLE-3 训练框架中可复用的部分：

target-generated data
hidden state extraction
training loop / optimizer / checkpoint
acceptance eval harness
vocab mapping / lm_head sharing

不能直接复用或必须重写的部分：

sample construction
forward signature
attention mask
loss weighting
block metrics
draft/verify cache semantics
checkpoint config fields
