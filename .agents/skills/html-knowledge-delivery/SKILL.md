# HTML Knowledge Delivery

将知识库中已经建立的领域知识整理成可阅读、可探索、可追溯的 HTML 补充件。HTML 负责解释和呈现；canonical Markdown 仍负责保存正式结论与证据。默认使用中文；用户指定其他语言时遵从用户。

## 适用边界

- 适用于新建或实质修订领域 HTML、主题导航页、对比页、交互式知识图谱式页面。单纯修复一个错字或链接时，只做局部修复。
- 在本仓库工作时，先完整读取根目录 `AGENTS.md` 和 `00_meta/research-knowledge-organization.md`；遵循其 owner、路径、链接、资产、验证和提交规则。需要新增或实质修改 canonical Markdown 时，另按适用的研究及发布 skill 执行。
- HTML 的内容来源优先是现有 README、Survey、Topic、Paper、Evidence 与正式资产。材料不足时标出缺口并回到来源核验；不把猜测写成事实，不因制作 HTML 而复制或新建第二份 canonical 论文分析。

## 工作方法

### 1. 确定问题与边界

明确页面要回答的读者问题、目标读者、涉及的 domain、现有 canonical 入口和预期更新路径。先查同域已有页面与主题；可以复用的内容优先复用或增量修订。明确每条关键论断的证据位置、版本及尚未核实的部分。

### 2. 先整合主题，再设计页面

把候选 Topic 按共同问题、作用环节、机制或决策场景聚合。对相似 Topic，先抽出共同概念和因果链，再说明各自的适用条件、关键差异、取舍与边界；对互补 Topic，展示它们如何衔接。不要为每个 Topic 机械生成一张互不关联的卡片，也不要把目录、术语表或原文段落当作综合分析。

每个主要知识组至少回答：它解决什么问题；为什么需要这些做法；相关做法之间是什么关系；在什么条件下选择或组合；哪些结论有证据，哪些仍是解释或待核验。比较表用于并排查阅；因果关系和判断依据仍要写成连贯文字。

### 3. 设计渐进式披露

首屏呈现领域主线、知识组和读者下一步可做的选择。每个条目默认显示名称、可辨认的场景或核心判断，以及一到两项关键事实；展开后再给机制、对比、证据与实现细节。长表、原始字段、例外条件和出处放在更深一层，但关键结论不能藏到用户难以发现的层级。

信息范围大到一个页面出现多条独立阅读主线、过长的导航或大量需要连续展开的细节时，建立一个概览页和按问题/知识组划分的子页面。概览页保留关系地图与结论入口，子页面承载深入解释；提供清晰的返回路径和跨页链接。不要仅靠无限折叠来容纳本应分开的内容。页面数量由内容边界决定，不预设固定页数。

### 4. 写清事实逻辑与术语

按“背景问题 → 机制或过程 → 结果/证据 → 适用边界”组织解释。事实、来源主张、跨来源综合判断和推断须可区分；有数字时注明口径、版本、单位和条件，存在矛盾时说明差异而非选一个数字掩盖。

第一次出现的缩写、英文术语、论文符号和框架名，在就近位置写出中文含义及其作用；无法自然解释时改用普通语言。标题、卡片摘要、图例、图表标题、筛选项、按钮与提示文字同样遵守此规则。代码/API 标识符可保留精确拼写，但必须说明它在流程中做什么。禁止只用缩写、黑话或源代码类名来承担解释。

### 5. 实现统一的页面系统

延续领域现有 HTML 的字体、配色、间距、卡片、导航和交互习惯；缺少既有规范时先建立一套可复用的视觉变量和组件规则，并在同一交付范围内一致应用。优先使用语义化 HTML、键盘可操作的导航和折叠、明确的焦点状态、窄屏可读布局。交互脚本用于发现和披露信息，核心内容在脚本不可用时仍应可读。

导航反映知识关系，而非仅反映文件结构。筛选或搜索不应成为发现主要结论的唯一途径。不要用视觉强调程度暗示尚未证实的结论已经确立。

## 交付检查

1. **内容结构：** 对照来源确认主要 Topic 已归组，相似与互补关系已解释，关键差异、适用条件和未解问题可定位；不存在只按 Topic 逐条罗列的主体页面。
2. **逐级阅读：** 未操作时能看懂页面主线和每个条目的价值；展开与跨页后能找到细节和证据；内容过密时已经合理拆页，链接可往返。
3. **语言与事实：** 通读所有可见文本，消除未解释的缩写和黑话；核对数值、版本、口径、来源链接与推断标识。自动搜索只能辅助，不能代替人工通读。
4. **视觉与交互：** 在桌面和手机宽度渲染检查阅读顺序、换行、对齐、溢出、展开、导航、筛选及键盘操作；修复发现的问题后重新检查。
5. **仓库发布：** 确认 HTML 位于对应 `supplements/`，canonical Markdown 链接和正式资产满足仓库规范；执行适用的领域 publisher validator、链接与 Git 检查，仅提交本任务文件。Paper review 或 promotion-plan 验证只在本任务实际修改相关交付类型时执行，不虚报通过。

交付说明列出页面范围、主要整合判断、已核验来源、运行过的检查及剩余缺口。
